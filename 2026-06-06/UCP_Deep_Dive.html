UCP: Universal Commerce Protocol

UCP는 agentic commerce의 “상거래 실행 언어”다. 에이전트가 상품 탐색, 장바구니, 체크아웃, 주문, 멤버십/계정 연결, 결제 핸들러를 merchant마다 별도 연동 없이 사용할 수 있게 만드는 표준이다.

1. Executive Summary

핵심 역할UCP는 결제 프로토콜이 아니라 commerce capability/discovery/checkout/order protocol이다. 결제 신뢰는 AP2와 payment handler가 맡는다.
왜 지금 중요한가Google, Shopify, 대형 리테일/결제사들이 agentic shopping의 표준 접점을 만들고 있다. AI Mode, Gemini, Universal Cart로 실제 소비자 접점에 붙기 시작했다.
AI 플랫폼 포인트대화형 AI 서비스, 커머스, 쇼핑, 예약, 지도, 로컬, 결제를 가진 AI 플랫폼은 UCP식 capability profile을 만들 수 있는 강한 후보군이다.
브리핑 한 줄: UCP는 “AI가 추천하는 쇼핑”이 아니라 “AI가 실제로 구매/예약/주문을 실행하는 커머스 운영체제”에 가깝다.

2. What It Is

Core Concepts Specification GitHub

공식 문서 기준 UCP는 platform, agent, business가 상거래 기능을 상호운용할 수 있도록 하는 open standard다. 기존 commerce API가 각 쇼핑몰 또는 플랫폼별로 따로 붙어야 했다면, UCP는 business가 한 번 capability를 선언하고, agent/platform이 이를 발견하고 협상해 실행하는 모델이다.

UCP가 다루는 범위는 제품 검색, catalog lookup, cart building, checkout, identity linking, order management, post-purchase status까지다. 즉 “상품을 찾아라”부터 “주문 상태와 반품/환불 이벤트를 추적하라”까지 commerce lifecycle 전체를 겨냥한다.

다른 프로토콜과의 관계

프로토콜UCP와의 관계
AP2agent가 결제할 때 사용자 의도와 결제 권한을 증명하는 trust layer. UCP checkout에 AP2 mandate extension으로 결합된다.
A2Aagent-to-agent transport 또는 business agent discovery 경로로 사용 가능하다.
MCPagent가 UCP capability를 tool처럼 호출하는 transport/binding이 될 수 있다.
AG-UI / A2-UI사용자가 cart, checkout, approval, order 상태를 보는 UI/interaction layer로 붙을 수 있다.

3. Technical Model

Schema Reference Versioning UCP + AP2
RolesPlatform/Application/Agent가 business capability를 소비하고, Business는 capability를 노출한다. Credential Provider는 payment/shipping/PII를 안전하게 관리하고, PSP는 결제 처리 인프라를 담당한다.
DiscoveryBusiness는 /.well-known/ucp에 profile을 발행한다. Platform은 요청마다 UCP-Agent header로 자기 profile을 알리고, business가 capability intersection을 계산한다.
Capabilitiesdev.ucp.shopping.checkout, cart, catalog.search, catalog.lookup, order, identity_linking처럼 독립 버전의 기능 단위로 구성된다.
ExtensionsDiscount, fulfillment, buyer consent, AP2 mandate 같은 확장 기능은 checkout/cart 같은 base capability 위에 composition된다.
TransportREST, MCP, A2A, Embedded transport를 모두 지원한다. agent는 MCP를 선호할 수 있고, 전통적 서버 연동은 REST가 적합하다.
SecurityOAuth 2.0, HTTP Message Signatures, API key, mTLS를 지원한다. Profile은 capability와 signing key discovery를 같이 제공한다.

핵심 설계 포인트

  • Capability negotiation: 양쪽이 모두 지원하는 capability와 version만 활성화한다.
  • Merchant of Record 유지: UCP는 플랫폼이 판매자가 되는 모델이 아니라 business가 MoR로 남는 구조를 강조한다.
  • Payment decoupling: payment instrument와 payment handler/processor를 분리해 다양한 wallet/PSP를 수용한다.
  • Identity linking: OAuth 기반으로 loyalty, member price, saved address 같은 authenticated commerce를 agent surface에서도 유지한다.
  • Date-based versioning: capability와 protocol version이 날짜 기반으로 관리된다.

5. AI Platform Implications

AI 플랫폼에 맞는 해석

AI 플랫폼은 UCP를 “해외 shopping protocol”로만 보면 안 된다. conversational surface, 커머스/쇼핑/예약/로컬/지도, 결제 서비스, 사용자 계정, 채널/파트너 생태계를 가진 쪽에서 UCP식 profile과 capability negotiation은 직접적인 플랫폼 설계 문제다.

AI 플랫폼 자산UCP식 capability 후보설계 질문
커머스 / 쇼핑catalog.search, cart, checkout, orderagent가 상품 비교, 옵션 선택, 결제, 배송지 확인을 한 흐름으로 실행할 수 있는가?
결제 서비스payment handler, AP2 mandateagent 결제 승인과 증빙을 payment-service trusted surface에서 처리할 수 있는가?
사용자 계정 / 멤버십identity_linking대화형 서비스 안에서 partner benefit, 쿠폰, 포인트, 등급 혜택을 안전하게 연결할 수 있는가?
지도 / 로컬 / 예약lodging, food, reservation extension커머스가 상품 구매뿐 아니라 예약, 주문, 픽업, 배달로 확장되는가?
채널 / 파트너business profile onboarding중소 merchant가 쉽게 capability profile을 발행하도록 도와줄 수 있는가?

6. Recommended Actions

  1. AI 서비스 UCP Profile Draft: /.well-known/agent-commerce 또는 UCP-compatible profile schema 초안을 만든다.
  2. Merchant Capability Pilot: 커머스/쇼핑에서 catalog, cart, checkout, order 네 가지 capability만 먼저 pilot한다.
  3. AP2 결합 설계: checkout completion 전 payment-service trusted surface에서 mandate를 발행하는 흐름을 설계한다.
  4. AG-UI/A2-UI 프론트 결합: cart 비교, 배송지 선택, 결제 승인, 주문 추적을 agent UI event와 declarative UI로 분리한다.
  5. 리스크 검토: 가격/재고 불일치, 환불/취소 책임, 판매자 고지 의무, 개인정보/결제정보 위임, 전자상거래법/전자금융 규제 검토를 병행한다.
주의: UCP는 아직 빠르게 바뀌는 표준이다. 바로 전면 도입보다 “UCP-compatible internal profile + service-specific extension”으로 시작하는 편이 안전하다.
